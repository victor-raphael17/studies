Protegendo a BookShelf API com sessão e Laravel Sanctum

Na Aula 1, construímos a API de livros e gêneros e deixamos suas rotas públicas. Agora vamos continuar esse mesmo projeto: cadastro e login criam uma sessão, o navegador guarda o cookie e o Laravel exige autenticação para acessar o catálogo.

Introdução — estado inicial da API

Partimos do estado final da aula anterior: o Laravel 12 já tem Sanctum instalado por php artisan install:api, o banco já foi migrado e routes/api.php expõe os CRUDs de genres e books sem autenticação. Nesta aula, vamos manter os controllers, services, Form Requests e Resources do catálogo e alterar o acesso às rotas.

A Aula 1 sobe o Laravel em http://localhost:8000. Para acompanhar sem criar outro projeto de frontend, abra esse endereço no navegador e use o Console das ferramentas de desenvolvedor como cliente temporário. As chamadas para /api e /sanctum ficam na mesma origem da página.

Use o mesmo host e a mesma porta em todas as chamadas. localhost:8000 e 127.0.0.1:8000 são origens diferentes; se preferir o segundo, troque também o domínio stateful no .env. O endereço 0.0.0.0 serve para o servidor escutar conexões, não para abrir a página no navegador.

O nome pode confundir

/sanctum/csrf-cookie prepara a proteção CSRF. Esse cookie não faz o login. Quem identifica o usuário é o cookie de sessão, criado depois do login. O token CSRF ajuda o Laravel a confirmar que uma operação como cadastro, atualização ou exclusão veio do seu frontend.

Somente para estudo local

O cadastro fica público e todas as contas podem alterar o mesmo catálogo. Antes de publicar, decida quem pode criar contas e implemente propriedade dos dados e regras de acesso.

Como ler os trechos alterados

Nos arquivos que já existiam, o fundo verde com + indica linhas adicionadas; o fundo vermelho com − indica linhas removidas; linhas sem destaque continuam iguais. O botão Copiar ignora as linhas removidas.

O que você precisa ter

  • O projeto e o banco do BookShelf funcionando como ficaram ao fim da Aula 1.
  • Laravel Sanctum instalado por php artisan install:api e a tabela users criada pelas migrations da Aula 1.
  • O servidor Laravel acessível em http://localhost:8000 e essa mesma página aberta no navegador.

Passo 1 Como o navegador mantém o login

Depois do login, o Laravel cria uma sessão e devolve um cookie. O navegador envia esse cookie automaticamente nas próximas chamadas para o mesmo site. A API usa a sessão para saber qual usuário está fazendo cada requisição.

  1. O frontend chama /sanctum/csrf-cookie.
  2. O frontend envia e-mail e senha para /api/login.
  3. O Laravel cria a sessão e devolve o cookie de sessão.
  4. O navegador envia o cookie nas próximas chamadas à API.

Em operações que mudam dados, como POST, PUT, PATCH e DELETE, o frontend também envia o valor do cookie XSRF-TOKEN no cabeçalho X-XSRF-TOKEN. O Laravel compara esse valor com a sessão.

Como a página de teste e a API usam a mesma origem, o navegador envia os cookies sem configuração de CORS. Aqui o próprio servidor Laravel atende a página, /api e /sanctum.

Para este projeto

A autenticação é feita pelo navegador do usuário. Se o seu servidor de frontend fizer chamadas ao Laravel por conta própria, sem passar pelo navegador, esse é outro fluxo e não usa automaticamente os cookies do navegador.

Para encurtar ou alongar a sessão, ajuste SESSION_LIFETIME em minutos no .env. Por exemplo, SESSION_LIFETIME=120 mantém a sessão por até duas horas sem atividade.

Passo 8 Conferindo no navegador

Abra as ferramentas de desenvolvedor do navegador, selecione a aba Network e percorra o fluxo:

  1. GET /sanctum/csrf-cookie responde e cria o cookie XSRF-TOKEN.
  2. POST /api/register responde 201, cria a conta e inicia a sessão.
  3. GET /api/me responde 200 com os dados do usuário.
  4. GET /api/books responde 200 com o catálogo.
  5. POST /api/logout responde 204.
  6. Uma nova chamada a GET /api/me responde 401.
  7. POST /api/login responde 200 e inicia outra sessão.

Nas chamadas que alteram dados, confira se o frontend envia X-XSRF-TOKEN. Nenhuma chamada de navegador precisa enviar Authorization: Bearer.

Erros comuns

  • 401: não há sessão válida. Confira se o login funcionou e se o navegador enviou o cookie de sessão.
  • 419: o token CSRF não chegou ou não corresponde à sessão. Faça de novo a chamada a /sanctum/csrf-cookie e envie X-XSRF-TOKEN.
  • 422: algum dado enviado não passou pela validação.

Passo 9 O que falta para produção

  • Use HTTPS e mantenha SESSION_SECURE_COOKIE=true em produção.
  • Decida se o cadastro público deve continuar aberto.
  • Defina quem pode ver, criar, editar e apagar livros. A autenticação confirma quem é o usuário; Policies e regras de propriedade decidem o que ele pode fazer.
  • Não registre cookies de sessão ou cabeçalhos CSRF em logs.

Adendo Migrando de Bearer para sessão e CSRF

Se você seguiu uma versão anterior do tutorial que emitia Bearer tokens, use este adendo para migrar o cliente navegador para o fluxo desta aula.

As instruções de tokens abaixo presumem que a versão antiga usava Personal Access Tokens do Sanctum. Se ela usava JWT ou outro pacote, o frontend ainda pode migrar para sessão, mas o middleware antigo precisa ser tratado conforme esse pacote.

São duas funções diferentes

O Bearer token identificava o usuário. No fluxo novo, quem autentica é o cookie de sessão; o cookie XSRF-TOKEN e o cabeçalho X-XSRF-TOKEN protegem as operações que alteram dados contra CSRF. O token CSRF não substitui a credencial de autenticação.

1. Reaproveite as rotas do catálogo

Mantenha o grupo auth:sanctum protegendo books e genres. Com statefulApi() e o domínio do navegador configurados como no Passo 2, esse guard aceita a sessão do navegador. Os controllers, services e Resources do catálogo não precisam mudar.

Se a versão antiga já tinha um POST /api/login para emitir Bearer, substitua a implementação pela versão de sessão do Passo 4. Não mantenha duas rotas com o mesmo método e caminho. Se um app mobile ou script ainda precisa emitir e revogar Bearer tokens, reserve caminhos próprios para esse cliente, por exemplo POST /api/tokens e DELETE /api/tokens/current. Proteja a rota de revogação com auth:sanctum, mantenha-a exclusiva para clientes Bearer e continue enviando o cabeçalho Bearer nesses pedidos.

2. Troque as chamadas do navegador

Remova a leitura do token salvo e o cabeçalho Authorization. Antes de cadastro ou login, chame /sanctum/csrf-cookie; depois, use o helper do Passo 6 para enviar o cookie de sessão automaticamente e o cabeçalho CSRF nas operações que alteram dados:

O helper completo do Passo 6 só adiciona X-XSRF-TOKEN em POST, PUT, PATCH e DELETE. Remova também o salvamento do Bearer token em localStorage ou sessionStorage. Peça que cada usuário faça login novamente: um Bearer token existente não se transforma em sessão.

3. Decida como tratar os tokens existentes

  • Se só o navegador usava Bearer, migre o frontend e revogue os tokens antigos depois que os usuários fizerem login novamente.
  • Se outros clientes ainda usam Bearer, mantenha a emissão desses tokens em uma rota separada e preserve o trait HasApiTokens e a tabela personal_access_tokens enquanto forem necessários.
  • O logout de sessão desta aula encerra a sessão do navegador; ele não revoga os Bearer tokens de outros dispositivos. Mantenha um fluxo separado para revogá-los.

Não apague a tabela personal_access_tokens nem revogue tokens em lote como parte automática da migração. Com Personal Access Tokens do Sanctum e o trait HasApiTokens mantidos, o guard pode aceitar sessões stateful e Bearer tokens nas mesmas rotas protegidas; os tokens antigos continuam válidos enquanto a aplicação os aceitar e eles não forem expirados ou revogados. Para um frontend em outra origem ou subdomínio, configure cookies com credenciais e CORS conforme a documentação do Sanctum.
