Curso de Programação — Módulo 5

BookShelf API protegida: autenticação com Laravel Sanctum

A continuação direta do módulo anterior. Você já tem uma API REST completa — e completamente aberta. Aqui vamos fechá-la usando uma das duas modalidades do Sanctum: API tokens Bearer, com rotas privadas, revogação instantânea e, o assunto que quase todo tutorial esquece, tokens que expiram.

Introdução — de API aberta a API protegida

No Módulo 4 construímos a BookShelf API: dez endpoints de genres e books, arquitetura Model-Service-Controller, validação com Form Requests e respostas formatadas por API Resources. E terminamos com um aviso desconfortável: qualquer pessoa com um curl pode apagar a sua estante inteira.

Este módulo paga essa dívida. Na implementação que construiremos, a API vai exigir um token Bearer válido em toda operação sobre a estante e ganhará cinco endpoints para gerenciar esses tokens:

MétodoRotaAçãoAcesso
POST/api/registerCria uma conta e devolve o primeiro tokenPúblico
POST/api/loginAutentica e devolve um token novoPúblico
GET/api/meDados do dono do token atualBearer
POST/api/logoutRevoga o token usado nesta requisiçãoBearer
POST/api/logout-allRevoga todos os tokens do usuárioBearer
/api/genres e /api/booksOs 10 endpoints do Módulo 4, intactosBearer

Escopo deste módulo

O Sanctum também autentica uma SPA própria com cookie de sessão, mas esse não é o fluxo que construiremos aqui. Nosso cliente de exercício é curl/Postman e o mesmo desenho atende apps mobile, scripts e integrações. Se a BookShelf ganhar um front-end React/Vue/Next/Nuxt de primeira parte no navegador, compartilhando o mesmo domínio de topo da API, a recomendação muda: use o modo SPA por cookie e não entregue a ele os tokens pessoais criados neste módulo. O Passo 1 separa os dois cenários sem atalhos.

O que você precisa ter em mãos

  • O projeto do Módulo 4 funcionando: php artisan migrate:fresh --seed reconstrói o banco e os 10 endpoints respondem. Se ainda não é o caso, volte e termine o tutorial anterior — este continua exatamente de onde ele parou.
  • O ambiente Docker do Passo 2 daquele módulo: MySQL no container, PHP local ou no container.
  • Nada de novo para instalar. O Sanctum já está no projeto desde o php artisan install:api — só nunca foi usado.

Como este tutorial funciona

Mesmo ritmo do módulo anterior, em três tempos: Conceito (o que é e por que existe), Mão na massa (comandos e código) e Como verificar (checklist que o navegador memoriza). Os blocos de código seguem o mesmo código de cores:

  • Verde — comandos de terminal (shell).
  • Azul — código PHP (o cabeçalho mostra o caminho do arquivo).
  • Âmbar — arquivos de configuração (.env, YAML, Dockerfile) e estruturas de pastas.
  • Cinza — saída: o que o terminal ou a API respondem. É para ler, não para rodar — por isso esses blocos não têm botão "Copiar".

Dentro de um bloco verde, o que é seu para digitar e o que é resposta da máquina nunca se misturam na hora de copiar. O botão "Copiar" entrega só os comandos: ele descarta as linhas de saída, o prompt > do tinker e as linhas removidas do diff. Copiar e colar funciona de primeira, sem selecionar nada na mão.

  • Texto claro — comando: é o que você roda.
  • Texto cinza — saída do comando anterior, mostrada para você comparar com a sua. Não é copiada.
  • Texto âmbar — valor de exemplo que você precisa trocar pelo seu antes de rodar (um token, um id).

E as marcações de diff, para arquivos que já existem:

  • Fundo verde com + — linha nova ou alterada: é o que você escreve no arquivo.
  • Fundo vermelho com − — linha que existia e deve ser removida (o botão "Copiar" já a ignora).
  • Sem destaque — linha que já estava no arquivo: mantenha como está.

Como no módulo anterior, os comentários dentro dos blocos de código estão em inglês.

Conceito

Autenticação não é autorização. Autenticação responde "quem é você?"; autorização responde "o que você pode fazer?". Este módulo trata inteiramente do primeiro. Isso significa que, ao final, qualquer usuário autenticado poderá editar os livros de qualquer outro — não existe dono no banco do BookShelf. Fechar essa porta é o assunto do próximo módulo (Policies e um user_id nas tabelas); voltamos a esse ponto no Passo 10.

Passo 1 Sessões, tokens e o lugar do Sanctum

Conceito: HTTP não lembra de você

O HTTP é stateless: cada requisição chega ao servidor como se fosse a primeira. Nada no protocolo diz "esta é a mesma pessoa que fez login há dois minutos". Toda autenticação, no fundo, resolve o mesmo problema — anexar uma prova de identidade a cada requisição. O que muda é a natureza da prova.

A escolha correta depende de quem é o cliente, não de a URL começar com /api:

AbordagemComo a prova viajaUse quando
Sessão + cookieO servidor guarda a sessão; o navegador recebe o cookie e o reenvia automaticamenteO cliente é sua interface web de primeira parte: tanto Blade quanto uma SPA própria
API token no headerO cliente guarda uma string e a envia explicitamente em Authorization: Bearer ...O cliente é mobile, CLI, script, outro servidor, Postman ou uma integração confiável

Uma SPA continua sendo uma aplicação no navegador. Se ela é o seu próprio front-end e compartilha o mesmo domínio de topo com a API, o Sanctum recomenda sessão + cookie. Front-end e API podem estar em repositórios distintos e até em subdomínios diferentes, como app.exemplo.com e api.exemplo.com. Nesse modo há configuração de domínios, credenciais CORS e proteção CSRF; isso não torna o cookie inadequado — faz parte do mecanismo seguro para navegadores.

Neste módulo não construiremos uma interface web. Usaremos curl e Postman como clientes de uma API por token e assumiremos como cenários futuros um app mobile, um script ou uma integração. Por isso escolhemos Bearer token. É uma decisão de escopo, não a regra genérica “API usa token; SPA não usa cookie”.

Regra de bolso

Seu próprio front-end no navegador, compartilhando o domínio de topo da API? Sessão + cookie. Mobile, script, CLI, servidor ou integração confiável? No Sanctum, API token Bearer. Um aplicativo de terceiros precisa pedir acesso delegado à conta do usuário? Aí o problema é OAuth2, normalmente com Passport.

Conceito: a anatomia de uma requisição autenticada

No modo escolhido para este módulo, depois do login toda requisição protegida carrega um cabeçalho a mais. É só isto:

A palavra Bearer ("portador") não é decoração: ela descreve exatamente a natureza da coisa. Quem porta o token é o usuário, sem precisar de mais nada. Não há senha, não há segundo fator, não há pergunta. Guarde essa frase — ela é a justificativa de tudo o que faremos no Passo 7 sobre expiração.

Conceito: o que é o Laravel Sanctum

Sanctum é o pacote oficial e leve de autenticação web/API do Laravel. Ele faz duas coisas diferentes:

  1. API token authentication — emite tokens pessoais, guarda apenas seus hashes na tabela personal_access_tokens e os recebe no header Authorization. É o modo deste módulo.
  2. SPA authentication — não cria nem usa API token. Autentica a SPA própria com os serviços normais de sessão e cookie do Laravel. SPA e API precisam compartilhar o mesmo domínio de topo, embora possam estar em subdomínios e repositórios diferentes.

O guard auth:sanctum é a ponte entre os dois modos: quando a autenticação stateful da SPA está configurada, ele tenta primeiro a sessão por cookie; se não houver uma sessão autenticada, procura um Bearer token. As mesmas rotas de negócio podem, portanto, atender uma SPA própria e clientes por token. O que muda é o fluxo de login, armazenamento da credencial e logout.

E onde ele se encaixa entre as alternativas do ecossistema:

PacoteO que resolveQuando escolher
SanctumCookie/sessão para SPA própria e API tokens simplesInterface web de primeira parte, mobile e integrações que não precisam do protocolo OAuth2 completo
PassportServidor OAuth2 completoAplicativos de terceiros precisam receber acesso delegado à sua API em nome dos seus usuários
JWT (pacotes de terceiros)Tokens autocontidos e assinados, sem consulta ao bancoArquiteturas distribuídas em que vários serviços validam o mesmo token

Conceito

Token do Sanctum não é JWT. Um JWT é autocontido: os dados do usuário viajam dentro dele, assinados, e o servidor valida sem tocar no banco. Rápido — e com um preço alto: como nada é consultado, não dá para invalidar um JWT antes do prazo sem inventar uma lista de bloqueio (que, ironicamente, exige consultar o banco de novo). O token do Sanctum é o oposto: uma string aleatória e opaca, cujo hash vive numa linha do banco. Cada requisição faz uma consulta — e, em troca, apagar aquela linha revoga o acesso no mesmo instante. É essa troca que faz o logout do Passo 6 funcionar de verdade.

Conceito: a tabela personal_access_tokens

Toda a autenticação por Bearer token deste módulo gira em torno de uma única tabela. Vale conhecer coluna por coluna, porque cada uma vira um recurso concreto mais adiante:

ColunaPara que serve
idChave primária — e também o número que aparece antes da barra vertical no token entregue ao cliente
tokenable_type
tokenable_id		O dono do token, em formato polimórfico: App\Models\User + o id. É "polimórfico" porque qualquer model pode emitir tokens, não só User
nameUm rótulo livre para você identificar o token ("mobile-app", "integração do Zapier")
tokenO hash SHA-256 do token. O valor original não é guardado em lugar nenhum
abilitiesLista JSON de habilidades. O padrão é ["*"] — "pode tudo" (Passo 8)
last_used_atAtualizado pelo Sanctum a cada requisição autenticada. Ótimo para auditoria
expires_atValidade deste token. Nulo por padrão (Passo 7)
created_at / updated_atTimestamps. O created_at é o que o relógio global de expiração mede (Passo 7)

Essa tabela pertence somente ao modo de API tokens. No modo SPA por cookie, o login cria uma sessão do Laravel e não insere uma linha em personal_access_tokens; abilities, expires_at e revogação de tokens estudados adiante também não controlam a duração dessa sessão.

Conceito

Por que a coluna se chama token mas guarda um hash? Pela mesma razão pela qual você nunca guarda senhas em texto puro. Se o banco vazar, um invasor com a lista de hashes não consegue montar nenhum header Authorization válido — o SHA-256 não volta atrás. A consequência prática é dura e importante: o token em texto puro existe uma única vez, na resposta que o criou. Perdeu? Não há "ver token de novo". Gera-se outro.

E o número antes da barra (3|nQ8x...) é o id da linha. Sem ele, o Sanctum teria que comparar o hash contra a tabela inteira; com ele, vai direto na linha certa e faz uma única comparação — em tempo constante, com hash_equals().

Passo 3 O model User e o trait HasApiTokens

Conceito: o usuário que sempre esteve lá

O Laravel nasce com um model User e uma migration create_users_table. No Módulo 4 nós rodamos essa migration sem pensar duas vezes (foi o php artisan migrate do Passo 2) e depois ignoramos a tabela por doze passos. Ela está lá, vazia, esperando.

Para que um User possa emitir tokens, falta uma linha: o trait HasApiTokens, que o Sanctum fornece. É ele que dá ao model os métodos createToken(), tokens(), tokenCan() e currentAccessToken().

Conceito

O cast 'password' => 'hashed' faz o que você acha que precisa fazer na mão. Com ele, atribuir $user->password = 'secret123' guarda no banco o hash bcrypt daquela string, automaticamente. É por isso que, no service do próximo passo, você não vai ver nenhum Hash::make() — e não é esquecimento.

Em tutoriais mais antigos (e em código Laravel 9 ou anterior) você vai encontrar 'password' => Hash::make($data['password']) no registro. Continua funcionando: antes de hashear, o cast verifica com Hash::isHashed() se o valor já é um hash e, se for, não mexe. Ou seja, não existe risco de hashear duas vezes — mas, no Laravel 12, escrever isso é redundante.

Passo 4 Registro e login em quatro camadas

Conceito: autenticação também respeita a arquitetura

Nada aqui inventa uma estrutura nova. O fluxo de autenticação atravessa exatamente as mesmas quatro camadas que os gêneros e os livros atravessam desde o Módulo 4:

  1. Form Request valida o que chegou (e devolve 422 sozinho se algo estiver errado);
  2. Controller recebe os dados validados e delega;
  3. Service executa a regra de negócio — criar o usuário, conferir a senha, emitir o token;
  4. Resource decide o que do usuário vira JSON.

Mão na massa: os Form Requests

Seguimos o padrão do módulo anterior: embora o Laravel também aceite regras numa única string separada por |, usamos arrays como ['required', 'email'], em linha com os exemplos da documentação mais recente e prontos para receber objetos de regra quando necessário.

Como no Módulo 4, os arquivos nascem com authorize() retornando false — troque para true nos dois, senão toda requisição morre num 403 antes da validação rodar. Estas rotas são públicas por natureza: ninguém pode ter um token antes de fazer login.

Duas regras merecem tradução:

  • unique:users,email — o e-mail não pode existir na coluna email da tabela users. É a mesma família do exists:genres,id do Módulo 4, ao contrário;
  • confirmed — exige que o corpo traga também um campo password_confirmation com o valor idêntico. É a checagem de "digite a senha novamente", feita no servidor;
  • Password::min(8)->letters()->numbers() — em vez de uma string de regras, um objeto que descreve a política de senha: mínimo de 8 caracteres, ao menos uma letra e ao menos um número. Existem outros: ->mixedCase(), ->symbols() e o excelente ->uncompromised(), que consulta a base pública de senhas já vazadas.

Boa prática

Repare que o LoginRequest não repete a política de senha forte. E é proposital: aqui não estamos definindo uma senha, estamos conferindo uma. Se um usuário antigo tem uma senha de 6 caracteres, exigir Password::min(8) no login o trancaria para fora da própria conta com um 422 confuso. Valide formato na entrada; valide força só onde a senha é criada.

Mão na massa: a Resource do usuário

O $hidden do model já esconderia a senha; a Resource resolve o problema pelo outro lado, que é o mais seguro dos dois: em vez de listar o que não pode sair, ela lista o que pode. Adicione amanhã uma coluna cpf na tabela users e ela não vaza por descuido — simplesmente não está aqui.

Mão na massa: o AuthService

O coração do passo. Crie app/Services/AuthService.php, ao lado dos services que você já tem:

Linha a linha do que é novo:

  • User::create($data) — atribuição em massa filtrada pelo $fillable. O password_confirmation, que nem chega aqui (o validated() só devolve campos que têm regra), seria ignorado de qualquer forma;
  • Hash::check($senhaEnviada, $hashDoBanco) — aplica o mesmo algoritmo ao texto recebido e compara com o hash guardado. É a única maneira de "conferir" uma senha que você nunca teve;
  • $user->createToken('api-token') — cortesia do HasApiTokens: grava a linha em personal_access_tokens e devolve um objeto NewAccessToken, do qual tiramos o plainTextToken — a única vez em que ele existe;
  • throw new AuthenticationException(...) — e aqui vale uma parada.

Conceito

Uma exceção que vira resposta HTTP. É o mesmo mecanismo do findOrFail() do Módulo 4, que estourava uma exceção e o Laravel traduzia em 404. Aqui, o handler do framework converte AuthenticationException em 401 Unauthorized com {"message": "Invalid credentials."} — sem nenhum if ou response()->json(..., 401) da nossa parte. O service continua falando de negócio; o framework cuida do HTTP.

Por que 401 e não 422? Os starter kits oficiais (Breeze, Fortify) lançam ValidationException nesse ponto e respondem 422. Funciona, e você vai encontrar muito código assim. Preferimos 401 porque a distinção ajuda quem consome a API: 422 significa "seu pedido está malformado, corrija-o"; 401 significa "seu pedido está perfeito, suas credenciais é que não servem". Um cliente trata os dois casos de forma bem diferente.

Passo 5 Protegendo as rotas com auth:sanctum

Conceito: o middleware que faltava

No Passo 3 do Módulo 4 desenhamos o ciclo de vida de uma requisição, e o item 4 era: "os Middlewares são executados — camadas que inspecionam a requisição: CORS, autenticação etc.". Na época, a nota entre parênteses dizia "nesta etapa, só os padrões do framework". É agora que essa camada ganha função.

O middleware auth:sanctum se lê como "o middleware auth, usando o guard sanctum". Ele é híbrido e decide qual credencial examinar:

  1. Quando o modo stateful está configurado e a requisição vem da SPA de primeira parte, tenta autenticar pela sessão/cookie do guard web;
  2. Se não houver uma sessão autenticada, procura o header Authorization: Bearer ...;
  3. No ramo Bearer, separa o token no |, busca a linha pelo id, compara o hash e confere a expiração;
  4. Qualquer ramo que tenha sucesso disponibiliza o usuário em $request->user(); no ramo Bearer, o Sanctum também marca last_used_at;
  5. Se nenhum ramo autenticar a requisição, devolve 401 Unauthorized e o controller nem é chamado.

Este projeto não configurou o fluxo stateful de uma SPA nem um login de sessão. Portanto, nos testes deste módulo, o guard sempre chegará ao segundo ramo e procurará o Bearer token. O nome auth:sanctum, por si só, não significa “apenas token”.

Conceito

De onde vem o guard sanctum? Se você abrir config/auth.php procurando por ele, não vai achar: os guards listados lá são web e, dependendo da versão, api. Atenção — força bruta no login

Passo 6 me, logout e revogação de tokens

Conceito: sair é apagar uma linha

Numa aplicação com sessão, "sair" significa destruir a sessão no servidor. Com tokens, é ainda mais literal: logout é DELETE numa linha da tabela personal_access_tokens. Na requisição seguinte, o Sanctum procura aquele hash, não encontra, e devolve 401. É a revogação instantânea que o Passo 1 prometeu — e que um JWT, sozinho, não consegue entregar.

O trait HasApiTokens dá as duas ferramentas necessárias:

  • $user->currentAccessToken() — o model do token que autenticou esta requisição específica. Apagá-lo desconecta este aparelho e só ele;
  • $user->tokens() — o relacionamento com todos os tokens do usuário. Apagá-los é o "sair de todos os dispositivos".

Logout de token ≠ logout de sessão

O código abaixo é deliberadamente exclusivo do modo Bearer: apaga registros de personal_access_tokens. Numa SPA stateful, o logout correto encerra o guard web, invalida a sessão e regenera o token CSRF; logout-all deste módulo também não encerra sessões de navegador. Não misture os dois fluxos só porque ambos podem proteger as mesmas rotas com auth:sanctum.

Passo 7 Expiração de tokens

Conceito: por que um token precisa morrer

Volte à palavra do Passo 1: Bearer. Quem porta o token é o usuário. Agora pense em todos os lugares por onde essa string passa numa vida real — o armazenamento de um app mobile, os logs de um proxy mal configurado, o histórico do terminal, uma captura de tela num chamado de suporte, um .env commitado por engano ou o backup do celular de alguém.

Vazamentos acontecem. A pergunta que a expiração responde não é "como impedir o vazamento", e sim "por quanto tempo um vazamento continua útil para o atacante". Um token que expira em 24 horas transforma um incidente numa janela fechada. Um token sem validade transforma o mesmo incidente numa porta dos fundos permanente — que ninguém percebe, porque nada quebra.

E o padrão do Sanctum é justamente esse: tokens que nunca expiram. É uma escolha de conveniência do framework, não uma recomendação de segurança, e cabe a você mudá-la.

Isto não configura cookies de SPA

Todo este passo trata de personal access tokens. config/sanctum.php → expiration e a coluna expires_at não definem a duração da sessão de uma SPA. E, para sua própria SPA, não transforme o Bearer token deste tutorial em credencial persistida no localStorage: use o modo stateful por cookie descrito no Passo 1.

Conceito

Escolhendo o prazo. Não existe número certo, existe uma troca: prazo curto = menos janela para o atacante, mais interrupções para o usuário legítimo. Referências úteis do mercado — 15 minutos a 1 hora para operações sensíveis (bancos, painéis administrativos), quase sempre acompanhadas de um mecanismo de refresh; 1 a 30 dias para apps móveis, onde pedir login toda hora é inaceitável. Para a BookShelf, 24 horas é um meio-termo honesto e didático.

Passo 8 Habilidades: tokens que podem menos

Conceito: nem todo token precisa poder tudo

Até aqui, todo token nasce com ['*'] — "pode tudo o que o dono pode". É o token amplo que o login deste tutorial entrega a um cliente confiável, como o app mobile oficial da BookShelf. Mas imagine que você queira gerar um token para um script que só monta um relatório mensal da sua estante. Esse script precisa ler livros; não precisa poder apagar nada. Se o servidor dele for invadido, a diferença entre um token ['*'] e um token ['books:read'] é a diferença entre um susto e um desastre.

É esse o papel das abilities (habilidades): uma lista de permissões gravada dentro do próprio token, na coluna abilities.

Conceito

Habilidade não é cargo. É um erro comum tentar usar abilities como sistema de papéis ("admin", "editor"). Habilidade limita o que aquele token pode fazer em nome do usuário — ela nunca dá mais poder do que o usuário já tem. Quem decide que um usuário é administrador é o modelo de autorização da aplicação (Policies e Gates, assunto do próximo módulo). As duas coisas se complementam: o usuário precisa poder a ação e o token usado precisa permitir a ação.

No modo SPA por cookie não existe uma linha de personal access token com abilities. Por conveniência, o Sanctum faz tokenCan() retornar true em requisições da interface de primeira parte; por isso as Policies continuam sendo obrigatórias para decidir o que o usuário realmente pode fazer.

Atenção: este é um recorte didático

Não existe uma regra do domínio que justifique proteger somente a exclusão de livros. Nesta API, excluir um gênero pode ser ainda mais destrutivo: por causa do cascadeOnDelete() criado no Módulo 4, o banco também exclui todos os livros daquele gênero. A rota de livros foi escolhida abaixo apenas para demonstrar, com uma única rota, como uma habilidade é exigida.

Por isso, o token ['books:read'] deste exemplo não é um token somente leitura de verdade. O Sanctum só verifica uma habilidade nas rotas que recebem o middleware (ou cujo código chama tokenCan()); as demais continuam exigindo apenas autenticação. Numa API real, aplique uma matriz coerente de habilidades a todas as operações relevantes de books e genres — e proteja especialmente DELETE /api/genres/{id}. Aqui vamos comprovar somente o mecanismo de books:delete.

Três detalhes importam nessa declaração. O ->except('destroy') registra o resource sem a rota de exclusão, para não haver duas rotas DELETE disputando a mesma URL. O ->whereNumber('id') exige dígitos na rota DELETE explícita. E o ->whereNumber('book') que veio do Módulo 4 precisa continuar no resource, restringindo as rotas GET/PUT/PATCH que compartilham /books/{...}.

Por que só restringir o DELETE produz 405?

Se DELETE books/{id} rejeitar abc, mas GET|PUT|PATCH books/{book} ainda aceitarem qualquer texto, o Laravel reconhece a URL /api/books/abc nas rotas dos outros verbos. Como nenhuma delas aceita DELETE, a resposta correta do roteador é 405 Method Not Allowed. Quando ambos os parâmetros — id da rota explícita e book do resource — estão restritos, nenhuma rota reconhece essa URL e o resultado passa a ser 404 Not Found. Portanto, o whereNumber('id') isolado não basta para esta checklist.

Dica

Dentro de um controller ou service, a mesma checagem se faz em código: $request->user()->tokenCan('books:delete') devolve true/false. Use o middleware quando a regra vale para a rota inteira; use o tokenCan() quando ela depende de alguma condição do próprio dado.

E como nada disso quebra o que já existe: um token ['*'] — que é o que o nosso login emite — passa em qualquer verificação de habilidade. O curinga continua podendo tudo. A trava só morde tokens que foram deliberadamente restringidos.

Checklist de segurança para levar para a vida

  • HTTPS não é opcional. Um token no header viaja em texto puro; sem TLS, qualquer intermediário na rede o lê e passa a ser o usuário. Tudo o que fizemos aqui pressupõe transporte criptografado em produção;
  • Nunca registre o header Authorization em log. Vale para os seus logs, para os do proxy e para o serviço de monitoramento de erros — que costuma capturar headers por padrão;
  • Não entregue personal access token à sua SPA de primeira parte. Use o modo stateful do Sanctum, com sessão, cookie e proteção CSRF; Bearer token persistido no localStorage não é o fluxo recomendado para esse cliente;
  • Trocou a senha, derrube os tokens ($user->tokens()->delete()). Senha nova com token velho ativo é segurança de fachada;
  • Considere um prefixo nos tokens. A opção token_prefix do config/sanctum.php faz cada token começar com uma marca sua (bookshelf_...). Serviços de secret scanning como o do GitHub usam esses prefixos para detectar segredos commitados por engano e avisar antes que alguém os use;
  • Prazo curto por padrão. Se estiver em dúvida entre 1 dia e 30 dias, comece pelo menor: alongar um prazo é fácil, recolher um token vazado é impossível.

Para onde ir agora

Em ordem de importância para a sua API:

  • Autorização e propriedade dos dados — o buraco que este módulo deixou aberto de propósito. Hoje, a Ada autenticada pode apagar os livros do usuário demo, porque livro nenhum tem dono. O caminho: uma migration adicionando user_id em genres e books, o escopo por usuário nos services e Policies decidindo quem pode o quê;
  • Testes automatizados — o Sanctum tem um atalho feito para isso: Sanctum::actingAs($user) autentica um usuário dentro do teste sem precisar de login nem de header. Junte com as factories que o trait HasFactory dos models já habilita desde o Módulo 4;
  • Renovação de token — implemente uma rota POST /api/refresh que revoga o token atual e emite um novo, para o cliente renovar antes do expires_at sem pedir a senha de novo;
  • Verificação de e-mail e recuperação de senha — o Laravel já traz a estrutura (MustVerifyEmail, notifications); é integrá-la ao fluxo de registro;
  • Modo SPA do Sanctum — se a BookShelf ganhar uma SPA própria que compartilhe o mesmo domínio de topo com a API, implemente a modalidade stateful recomendada: $middleware->statefulApi(), domínios/CORS com credenciais, chamada inicial a /sanctum/csrf-cookie e login pelo guard web. SPA e API podem estar em subdomínios e repositórios diferentes; não é necessário servir os dois juntos.
