Curso de Programação — Módulo 5

BookShelf API protegida: sessão e cookie com Laravel Sanctum

A API do Módulo 4 está pronta, mas qualquer pessoa pode usá-la. Neste módulo, vamos exigir login. O navegador vai manter a sessão em um cookie e enviar um token CSRF nas operações que alteram dados.

Introdução — o fluxo deste módulo

Vamos proteger os endpoints de genres e books e criar rotas de cadastro, login, usuário atual e logout.

O frontend deste exemplo roda no navegador em https://www.meusite.com. A API fica disponível em https://www.meusite.com/api e é encaminhada por outro Nginx. Para o navegador, página e API têm a mesma origem: o protocolo, o domínio e a porta são iguais. O Nginx que recebeu cada caminho não muda isso.

MétodoRotaO que faz
POST/api/registerCria a conta e inicia a sessão
POST/api/loginConfere e-mail e senha e inicia a sessão
GET/api/meRetorna o usuário conectado
POST/api/logoutEncerra a sessão
/api/genres e /api/booksRotas do Módulo 4; agora exigem login

O nome pode confundir

/sanctum/csrf-cookie prepara a proteção CSRF. Esse cookie não faz o login. Quem identifica o usuário é o cookie de sessão, criado depois do login. O token CSRF ajuda o Laravel a confirmar que uma operação como cadastro, atualização ou exclusão veio do seu frontend.

Somente para estudo local

O cadastro fica público e todas as contas podem alterar o mesmo catálogo. Antes de publicar, decida quem pode criar contas e implemente propriedade dos dados e regras de acesso.

O que você precisa ter

  • O projeto do Módulo 4 funcionando.
  • Laravel Sanctum instalado pelo php artisan install:api. O Módulo 4 já fez isso.
  • O Nginx público encaminhando /api/* e /sanctum/* para o Laravel, mantendo o domínio público da requisição.

Passo 1 Como o navegador mantém o login

Depois do login, o Laravel cria uma sessão e devolve um cookie. O navegador envia esse cookie automaticamente nas próximas chamadas para o mesmo site. A API usa a sessão para saber qual usuário está fazendo cada requisição.

  1. O frontend chama /sanctum/csrf-cookie.
  2. O frontend envia e-mail e senha para /api/login.
  3. O Laravel cria a sessão e devolve o cookie de sessão.
  4. O navegador envia o cookie nas próximas chamadas à API.

Em operações que mudam dados, como POST, PUT, PATCH e DELETE, o frontend também envia o valor do cookie XSRF-TOKEN no cabeçalho X-XSRF-TOKEN. O Laravel compara esse valor com a sessão.

Como frontend e API usam a mesma origem, o navegador aceita os cookies sem configuração de CORS. O Nginx precisa apenas encaminhar os caminhos da API e do Sanctum ao Laravel.

Para este projeto

A autenticação é feita pelo navegador do usuário. Se o seu servidor de frontend fizer chamadas ao Laravel por conta própria, sem passar pelo navegador, esse é outro fluxo e não usa automaticamente os cookies do navegador.

Passo 7 Sessão e logout

O cookie mantém a sessão até o usuário sair ou ela expirar. O tempo é controlado pela configuração de sessão do Laravel, não por SANCTUM_TOKEN_EXPIRATION.

O botão de logout deve fazer um POST para /api/logout. O helper do passo anterior inclui o cabeçalho CSRF:

Depois disso, /api/me deve responder 401. O próximo login cria uma sessão nova.

Para encurtar ou alongar a sessão, ajuste SESSION_LIFETIME em minutos no .env. Por exemplo, SESSION_LIFETIME=120 mantém a sessão por até duas horas sem atividade.

Passo 8 Conferindo no navegador

Abra as ferramentas de desenvolvedor do navegador, selecione a aba Network e percorra o fluxo:

  1. GET /sanctum/csrf-cookie responde e cria o cookie XSRF-TOKEN.
  2. POST /api/login responde 200 e inicia a sessão.
  3. GET /api/me responde 200 com os dados do usuário.
  4. POST /api/logout responde 204.
  5. Uma nova chamada a GET /api/me responde 401.

Nas chamadas que alteram dados, confira se o frontend envia X-XSRF-TOKEN. Nenhuma chamada de navegador precisa enviar Authorization: Bearer.

Erros comuns

  • 401: não há sessão válida. Confira se o login funcionou e se o navegador enviou o cookie de sessão.
  • 419: o token CSRF não chegou ou não corresponde à sessão. Faça de novo a chamada a /sanctum/csrf-cookie e envie X-XSRF-TOKEN.
  • 422: algum dado enviado não passou pela validação.

Passo 9 O que falta para produção

  • Use HTTPS e mantenha SESSION_SECURE_COOKIE=true em produção.
  • Decida se o cadastro público deve continuar aberto.
  • Defina quem pode ver, criar, editar e apagar livros. A autenticação confirma quem é o usuário; Policies e regras de propriedade decidem o que ele pode fazer.
  • Não registre cookies de sessão ou cabeçalhos CSRF em logs.

Passo 11 Migrando de Bearer token para cookie

Se você já terminou uma versão da BookShelf que emite Bearer tokens, não precisa refazer os controllers de livros e gêneros. O Sanctum permite que as mesmas rotas com auth:sanctum aceitem sessão de navegador quando a configuração stateful estiver ativa.

1. Ative sessão e CSRF

Siga os Passos 2 e 4: habilite statefulApi(), configure SANCTUM_STATEFUL_DOMAINS e adicione o login por sessão. O frontend deve chamar /sanctum/csrf-cookie antes de fazer login.

2. Troque o fluxo do frontend

  • Remova a leitura e gravação do token em localStorage ou sessionStorage.
  • Pare de enviar Authorization: Bearer ... nas chamadas do navegador.
  • Faça login para receber o cookie de sessão e use X-XSRF-TOKEN nas operações que alteram dados.
  • Peça que o usuário faça login novamente. Um Bearer token existente não se transforma em uma sessão.

3. Decida o que fazer com os tokens antigos

Os tokens já emitidos continuam válidos enquanto o código ainda aceita Bearer e eles não expiraram ou foram revogados. Se algum app mobile, script ou integração ainda usa esses endpoints, mantenha o cadastro/login Bearer para eles e crie endpoints separados para a sessão do navegador, por exemplo /api/session/login e /api/session/logout. Os dois tipos de cliente podem usar as mesmas rotas de livros e gêneros protegidas por auth:sanctum.

Quando nenhum cliente precisar mais de Bearer, remova o código que emite tokens e revogue os tokens antigos. O comando abaixo apaga todos os tokens pessoais do Sanctum; use-o somente se nenhum outro cliente depender deles:

Depois de remover todo o código de emissão e uso de tokens, você pode tirar HasApiTokens do model User. A tabela personal_access_tokens pode ficar no banco; ela não interfere na autenticação por sessão. A configuração SANCTUM_TOKEN_EXPIRATION também não controla a duração da sessão: sessões usam SESSION_LIFETIME.

Se a API atende outros clientes

O logout de sessão encerra o cookie do navegador. Um cliente Bearer continua usando o logout que revoga o token enviado por esse cliente.
