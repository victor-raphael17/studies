BookShelf API: aprenda Laravel 12 construindo uma API REST completa

Um tutorial para quem nunca tocou em Laravel. A cada passo você aprende um conceito do framework e o aplica imediatamente no projeto BookShelf — uma API para gerenciar sua estante pessoal de livros, organizados por gênero literário.

Introdução — o que vamos construir

Ao final deste tutorial você terá uma API RESTful funcional, escrita em Laravel 12, que permite criar, listar, atualizar e excluir gêneros literários e livros. Cada livro pertence a um gênero. Estes são os endpoints que a sua API vai responder:

MétodoRotaAção
GET/api/genresListar todos os gêneros
POST/api/genresCriar um gênero
GET/api/genres/{id}Exibir um gênero
PUT/api/genres/{id}Atualizar um gênero
DELETE/api/genres/{id}Excluir um gênero
GET/api/booksListar todos os livros
POST/api/booksCriar um livro
GET/api/books/{id}Exibir um livro
PUT/api/books/{id}Atualizar um livro
DELETE/api/books/{id}Excluir um livro

Pelo caminho, você vai aprender os fundamentos do Laravel na ordem em que eles fazem sentido: instalação e ambiente, estrutura do projeto, arquitetura MVC, migrations e seeders, Eloquent ORM, controllers e rotas RESTful, a arquitetura Model-Service-Controller (MSC), validação com Form Requests, formatação de respostas com API Resources e as convenções PSR que a comunidade PHP segue.

O que você precisa saber antes de começar

  • PHP básico: variáveis, arrays, funções, classes e objetos.
  • Terminal: navegar entre pastas e executar comandos.
  • Noções de HTTP: saber que existem requisições e respostas. Os detalhes (verbos, status codes) explicamos aqui.
  • Nenhum conhecimento de Laravel. É sério: começamos do zero absoluto.

Como este tutorial funciona

Cada passo segue o mesmo ritmo, em três tempos:

  1. Conceito — primeiro entendemos o que é a peça do Laravel que vamos usar e por que ela existe.
  2. Mão na massa — aplicamos o conceito imediatamente no BookShelf: comandos para rodar e código para escrever.
  3. Como verificar — uma checklist para confirmar que tudo funcionou antes de seguir adiante. Marque os itens: o navegador lembra do seu progresso.

Os blocos de código são identificados por cor, para você nunca confundir o que digita no terminal com o que escreve em um arquivo:

  • Verde — comandos de terminal (shell).
  • Azul — código PHP (o cabeçalho mostra o caminho do arquivo).
  • Âmbar — arquivos de configuração (.env, YAML, Dockerfile) e estruturas de pastas.
  • Cinza — saída: o que o terminal ou a API respondem. É para ler, não para rodar — por isso esses blocos não têm botão "Copiar".

Dentro de um bloco verde, o que é seu para digitar e o que é resposta da máquina nunca se misturam na hora de copiar. O botão "Copiar" entrega só os comandos: ele descarta as linhas de saída, o prompt > do tinker e as linhas removidas do diff. Copiar e colar funciona de primeira, sem selecionar nada na mão.

  • Texto claro — comando: é o que você roda.
  • Texto cinza — saída do comando anterior, mostrada para você comparar com a sua. Não é copiada.
  • Texto âmbar — valor de exemplo que você precisa trocar pelo seu antes de rodar (um id, um token).

Além disso, quando um bloco mostra um arquivo que já existe sendo editado — em geral, um esqueleto gerado por php artisan make:... —, as linhas são marcadas como num diff do Git/GitHub:

  • Fundo verde com + — linha nova ou alterada: é o que você escreve no arquivo.
  • Fundo vermelho com − — linha que existia no arquivo e deve ser removida (o botão "Copiar" já a ignora).
  • Sem destaque — linha que já estava no arquivo: mantenha como está.

Uma escolha deliberada: os comentários dentro dos blocos de código estão em inglês. É a convenção dominante na indústria — e vale a pena se acostumar com ela desde o primeiro dia.

Conceito

O que é uma API REST? Uma API (Application Programming Interface) é uma aplicação sem telas: em vez de páginas HTML, ela recebe requisições HTTP e devolve dados — quase sempre em JSON. O estilo REST organiza essa conversa em torno de recursos (aqui, genres e books) manipulados pelos verbos HTTP: GET lê, POST cria, PUT atualiza e DELETE exclui.

Atenção

Nesta etapa do curso a API é totalmente pública: não usaremos middleware nem autenticação. Proteger as rotas é assunto para o projeto final. Um passo de cada vez.

Passo 1 Instalação e primeiro projeto

Conceito: o que é o Laravel (e o que é o Composer)

Laravel é um framework PHP: um conjunto de peças prontas e bem testadas — roteamento, acesso a banco de dados, validação, linha de comando — sobre o qual você constrói a sua aplicação. Em vez de reinventar essas peças, você escreve apenas o que é específico do seu projeto.

Composer é o gerenciador de dependências do PHP (o equivalente ao npm do JavaScript ou ao pip do Python). É ele quem baixa o Laravel e todas as bibliotecas de que o projeto precisa.

O Laravel também traz o Artisan, uma ferramenta de linha de comando (php artisan ...) que vamos usar o tempo todo: para subir o servidor, criar arquivos, rodar migrations e muito mais.

Passo 2 Ambiente com Docker

Atenção

Este passo é obrigatório. Neste curso, o MySQL sobe exclusivamente via Docker — não vamos instalar nem configurar MySQL direto na máquina. Já o PHP você pode continuar rodando localmente para desenvolver (como no Passo 1); o container PHP existe para garantir um ambiente idêntico ao dos colegas e para preparar o caminho da produção.

Conceito: por que Docker?

Docker executa aplicações em containers: pacotes isolados que carregam o programa e tudo de que ele precisa (versão exata do PHP, extensões, MySQL). O clássico "na minha máquina funciona" desaparece, porque a máquina passa a ser a mesma para todo mundo.

Nossa arquitetura terá dois serviços na mesma rede Docker:

  • mysql — o banco bookshelf, na porta 3306. É o único jeito de ter MySQL neste curso;
  • php — PHP 8.4 com a aplicação Laravel, expondo a porta 8000. Em desenvolvimento, você pode usar este container ou o PHP local da sua máquina.

Detalhe importante: dentro da rede Docker, o container PHP enxerga o banco pelo hostname do serviço. Ou seja, no .env o DB_HOST deixa de ser 127.0.0.1 e vira mysql. Já o PHP rodando na sua máquina continua enxergando o banco por 127.0.0.1, porque o compose publica a porta 3306 para fora do container.

Conceito: uma imagem para desenvolver, outra para publicar

O container PHP terá dois Dockerfiles, porque desenvolvimento e produção pedem coisas diferentes:

  • Dockerfile.dev — a imagem de desenvolvimento: instala todas as dependências (inclusive as de teste, como o PHPUnit) e serve a aplicação com o artisan serve, recarregando o código a cada requisição;
  • Dockerfile — a imagem de produção: instala só as dependências de runtime (--no-dev), otimiza o autoloader e habilita o OPcache, que guarda o PHP compilado em memória.

É uma convenção comum: o Dockerfile "sem sobrenome" é o de produção — é ele que pipelines de deploy procuram por padrão — e as variantes ganham sufixo (.dev).

Boas práticas aplicadas

Build apontando para o Dockerfile.dev: o compose é a ferramenta do dia a dia de desenvolvimento, então constrói a imagem de dev — o Dockerfile de produção fica reservado para o deploy. Versão fixa da imagem (mysql:8.4 em vez de latest) e healthcheck: sem ele, o depends_on só espera o container iniciar — e comandos como migrate podem falhar na primeira subida porque o MySQL ainda não estava pronto de verdade. Repare também no ping via 127.0.0.1 com --protocol=tcp, e não localhost: durante a inicialização, a imagem do MySQL sobe um servidor temporário que responde apenas pelo socket local — pingar por TCP garante que "healthy" significa "aceitando conexões de verdade".

Atenção ao volume

O bind mount .:/app sobrepõe o que foi copiado na imagem, inclusive o vendor/ gerado pelo composer install do Dockerfile. Em desenvolvimento, rode composer install na raiz do projeto na sua máquina, ou dentro do container: docker compose exec php composer install.

Conceito: o ciclo de vida de uma requisição

O que acontece quando alguém chama a nossa futura rota GET /api/genres? Este trajeto vai se repetir em tudo o que fizermos, então grave-o:

  1. O cliente faz uma requisição HTTP (ex.: GET /api/genres).
  2. O arquivo public/index.php — único ponto de entrada — inicia o framework.
  3. O Router procura em routes/api.php a rota correspondente.
  4. Os Middlewares são executados (camadas que inspecionam a requisição: CORS, autenticação etc. — nesta etapa, só os padrões do framework).
  5. O Controller processa a requisição e usa os Models necessários.
  6. A resposta volta ao cliente — HTML via Blade em sites, JSON em APIs como a nossa.

Passo 4 MVC: o mapa mental do Laravel

Conceito: as três camadas

Antes de escrever a primeira linha do BookShelf de verdade, precisamos do mapa mental que organiza todo projeto Laravel: o padrão arquitetural MVC (Model-View-Controller). Ele separa a aplicação em três camadas, cada uma com uma responsabilidade clara:

CamadaResponsabilidade
ModelRepresenta os dados e a lógica de negócio. Interage com o banco via Eloquent ORM.
ViewApresentação visual (templates Blade). Em APIs, é substituída por respostas JSON.
ControllerRecebe as requisições HTTP, coordena a lógica e retorna as respostas apropriadas.

A separação vale a pena por um motivo simples: cada tipo de mudança tem um endereço. Mudou uma regra de dados? Model. Mudou o formato da resposta? View. Mudou o fluxo de uma requisição? Controller.

Conceito: e numa API, cadê a View?

Em um site tradicional, a View é um template Blade que gera HTML. O BookShelf não tem telas: quem consome a API é outro programa (um app mobile, um front-end em JavaScript, o próprio curl). Nossa "View" é o JSON que devolvemos — e no Passo 9 ela vai ganhar forma explícita com as API Resources, classes cujo único trabalho é formatar a saída.

Traduzindo o MVC para o nosso projeto:

CamadaNo BookShelfOnde vive

ViewRespostas JSON (GenreResource, BookResource)app/Http/Resources/ (Passo 9)
ControllerGenreController, BookControllerapp/Http/Controllers/Api/ (Passo 7)

Conceito

Spoiler do Passo 8: em APIs, o MVC puro tem um ponto fraco — a lógica de negócio tende a inchar os Controllers. Quando chegarmos lá, vamos adicionar uma quarta peça, a camada Service, evoluindo para a arquitetura Model-Service-Controller (MSC). Primeiro o MVC clássico, depois o refinamento.

Passo 5 Banco de dados: migrations e seeders

Conceito: migrations são o controle de versão do banco

Uma migration é um arquivo PHP que descreve uma mudança estrutural no banco: criar uma tabela, adicionar uma coluna, criar um índice. Em vez de abrir o MySQL e rodar SQL na mão, você escreve a mudança em código e roda php artisan migrate. Vantagens:

  • Qualquer pessoa clona o projeto e reconstrói o banco idêntico com um comando;
  • O histórico do banco fica versionado junto com o código;
  • Cada migration tem um método up() (aplica a mudança) e um down() (desfaz).

Boa prática

Nunca altere o banco de dados manualmente. Toda mudança estrutural deve ser feita por migration; dados iniciais e de teste, por seeders e factories. Essa é uma das regras de ouro da comunidade Laravel.

Passo 6 Models e Eloquent: Genre e Book

Conceito: um ORM traduz objetos em tabelas

O Eloquent é o ORM (Object-Relational Mapper) do Laravel: ele mapeia cada tabela do banco para uma classe PHP — o Model — e cada linha para um objeto. Em vez de escrever SQL, você escreve Genre::all(), Book::create([...]), $genre->books.

A mágica se sustenta em convenções de nomenclatura: o model Genre (singular, PascalCase) é automaticamente ligado à tabela genres (plural, snake_case); Book à tabela books. Se você seguir a convenção, não precisa configurar nada.

Conceito: o que é o $fillable?

Métodos como Book::create($data) fazem atribuição em massa: preenchem várias colunas de uma vez a partir de um array. Isso é conveniente — e perigoso, se o array vier direto do cliente com campos que ele não deveria alterar. O $fillable é a lista de permissão: só as colunas listadas podem ser preenchidas em massa. Qualquer outro campo enviado é silenciosamente ignorado.

Conceito: relacionamentos hasMany e belongsTo

Um gênero tem muitos livros; um livro pertence a um gênero. Em Eloquent, isso vira um par de métodos:

  • Genre::books() retorna $this->hasMany(Book::class) — "tenho muitos livros";
  • Book::genre() retorna $this->belongsTo(Genre::class) — "pertenço a um gênero".

De novo, a convenção trabalha por nós: o Eloquent deduz que a ligação acontece pela coluna genre_id da tabela books (nome do método/model + _id) — exatamente a FK que criamos na migration. Com isso, $genre->books devolve a coleção de livros do gênero, e $book->genre devolve o objeto do gênero.

Conceito

E o enum e os nullable? A coluna status é um enum no banco: o MySQL rejeita qualquer valor fora de to_read, reading, finished. No PHP ela chega como string simples. Já os campos description, pages e rating podem ser null — e o JSON da API vai refletir isso. No Passo 9, a validação vai garantir esses contratos também na entrada da API.

Dica

Agora que os models existem, os seeders poderiam ser reescritos com Genre::create([...]) e Book::create([...]) — com timestamps automáticos. As duas formas são válidas; deixamos o DB::table() como está para você conhecer as duas. Abaixo, a título de comparação, o diff exato de cada arquivo.

Passo 7 Controllers e rotas RESTful

Conceito: os 5 métodos de um resource controller

Chegou a hora de expor os dados pela API. No estilo REST, cada recurso é manipulado por um conjunto padrão de operações, e o Laravel formaliza isso no resource controller: um controller com exatamente cinco métodos públicos, um por operação:

Método do controllerVerbo + rotaFaz o quêStatus de sucesso
indexGET /api/genresLista todos200 OK
storePOST /api/genresCria um novo201 Created
showGET /api/genres/{id}Exibe um200 OK
updatePUT /api/genres/{id}Atualiza um200 OK
destroyDELETE /api/genres/{id}Exclui um204 No Content

Os status codes fazem parte do contrato REST: 201 confirma criação, 204 significa "deu certo e não há corpo para devolver", 404 é "não encontrado" e 422 (Passo 9) é "dados inválidos".

Mão na massa: gerando os controllers

Quatro detalhes para prestar atenção:

  • Toda interação com o banco passa pelos Models (Genre::all(), Book::create()...), nunca por SQL no controller — requisito do projeto e boa prática geral;
  • findOrFail($id) busca pelo ID e, se não existir, lança uma exceção que o Laravel converte sozinho em resposta 404 — sem if nenhum da nossa parte;
  • response()->json($data, $status) monta a resposta JSON com o status HTTP escolhido;
  • response()->noContent() devolve exatamente o que o contrato do DELETE pede: corpo vazio com status 204.

Conceito

Você vai ver por aí: route model binding. Em muito código Laravel a assinatura seria show(Genre $genre) — o framework busca o registro e injeta o model pronto, com 404 automático. A pergunta certa para escolher entre binding e id explícito não é "qual é melhor?", e sim onde mora a busca no banco. O binding faz o fetch na camada de roteamento, antes do controller. Num projeto em que o controller fala direto com o Eloquent, isso é ótimo: menos código, 404 de graça. Mas no Passo 8 vamos refatorar para que só a camada Service toque o banco — e aí o binding jogaria contra: o findOrFail do service viraria código redundante, o acesso ao banco ficaria espalhado em duas camadas, e os services deixariam de ser autossuficientes (um job ou command que chamasse update($id, $data) teria que buscar o model por conta própria). Por isso, neste projeto, ids explícitos são a escolha coerente — não uma superioridade geral de um sobre o outro. Se um dia a URL usasse slug/UUID ou houvesse rotas aninhadas com escopo, a balança penderia de volta para o binding.

Uma aresta para conhecer (que, aliás, o binding não resolve de verdade): sem uma restrição numérica, um GET /api/genres/abc casa com a rota GET e tenta entregar a string abc ao parâmetro int $id do controller. Isso estoura um TypeError — status 500 — em vez de 404. Com binding implícito o mesmo request viraria WHERE id = 'abc', que retorna 404 no MySQL mas pode estourar 500 no Postgres.

Um 405 Method Not Allowed conta outra história: nenhuma rota aceitou o verbo enviado, mas o Laravel encontrou a mesma URL registrada para outro verbo. Imagine que somente DELETE books/{id} tenha ->whereNumber('id'), enquanto as rotas GET/PUT/PATCH de books/{book} continuem sem restrição. Em DELETE /api/books/abc, a rota DELETE rejeita abc, porém as rotas dos outros verbos ainda reconhecem a URL; por isso o roteador responde 405, e não 500 nem 404. Para obter 404, todas as rotas que compartilham esse segmento dinâmico precisam rejeitar o valor.

O nome dentro de whereNumber() ou Route::pattern() também precisa ser o nome real do parâmetro. Por padrão, apiResource('genres', ...) gera {genre} e apiResource('books', ...) gera {book}; portanto, whereNumber('id') e Route::pattern('id', '[0-9]+') não atingem essas rotas. Abaixo aplicaremos whereNumber('genre') e whereNumber('book') aos resources inteiros. Numa rota declarada como books/{id}, aí sim o nome correto é id. Como alternativa global, você pode definir padrões para genre e book, ou primeiro renomear os parâmetros dos resources para id.

Atenção

Este controller ainda tem uma falha proposital: $request->all() aceita qualquer entrada sem validar. Um POST sem name, por exemplo, vai estourar um erro de banco em vez de uma mensagem clara. O $fillable do Passo 6 já bloqueia colunas indesejadas, mas validação de verdade chega no Passo 9 — por enquanto, siga em frente sabendo dessa dívida.

Mão na massa: registrando as rotas com apiResource

Cada Route::apiResource registra de uma vez as cinco rotas RESTful (index, store, show, update, destroy) apontando para os métodos de mesmo nome do controller. Duas declarações, dez endpoints — exatamente a tabela da introdução.

Os dois whereNumber() fazem parte da implementação, não são uma dica opcional: o Laravel aplica a restrição a todas as rotas geradas pelo respectivo resource. Assim, um identificador não numérico morre no roteador com 404 antes de chegar ao controller, qualquer que seja o verbo HTTP.

Passo 8 Refatorando para MSC: a camada Service

Conceito: por que o MVC aperta em APIs

Nossos controllers estão saudáveis hoje, mas imagine as regras que uma estante real pediria: "não excluir um gênero com livros em leitura", "recalcular estatísticas ao terminar um livro", "notificar quando a meta de leitura for atingida". Se tudo isso for parar no controller, ele vira um monstro difícil de testar e manter — o famoso fat controller.

A solução consagrada em APIs é a arquitetura Model-Service-Controller (MSC): inserir uma camada Service entre o Controller e o Model para abrigar a lógica de negócio.

CamadaResponsabilidade
ControllerRecebe a requisição, valida os dados de entrada (via Form Request, Passo 9) e delega ao Service. Retorna a resposta HTTP.
ServiceContém a lógica de negócio. Orquestra operações entre Models e outros serviços.
ModelRepresenta a tabela no banco. Define relacionamentos, scopes e atributos.

Conceito

Por que usar Services? Controllers magros e Services focados facilitam testes unitários, reutilização da lógica em outros contextos (CLI, filas, eventos) e manutenção a longo prazo. O controller cuida do HTTP; o service cuida do negócio.

Aprofundando: eager loading e o problema N+1

Duas linhas do BookService merecem parar tudo: o Book::with('genre') do listAll() e do findById(). Sem esse with() o código continua funcionando — e é exatamente por isso que o N+1 é o problema de performance mais comum em APIs Laravel: ele não quebra nada, só deixa tudo lento, e em silêncio. Vamos ver o antes e o depois, em quatro tempos.

1. Sem eager loading, o gênero simplesmente não vem

Suponha que o service fizesse apenas Book::findOrFail($id), sem o with(). Esta seria a resposta de GET /api/books/1:

Olhe o que o cliente recebeu sobre o gênero: "genre_id": 1. Um número. Para escrever "The Hobbit — Fantasy" numa tela, o app precisa fazer uma segunda requisição, GET /api/genres/1. Numa listagem de 12 livros, são até 12 requisições extras — cada uma com uma viagem de rede inteira. O N+1 começa aqui, do lado de fora da API: uma consulta para a lista, mais N para completar cada item.

2. A saída ingênua: tocar em $book->genre dentro de um laço

"Fácil: eu embuto o gênero na resposta e pronto." E aí o Eloquent faz algo muito conveniente e muito caro — o lazy loading: na primeira vez que você toca em $book->genre, ele vai ao banco buscar aquele gênero. Uma consulta por livro. Dá para ver acontecendo com o registrador de consultas do Laravel, no tinker:

Treze consultas para montar uma lista de doze livros: 1 para os livros + N para os gêneros — daí o nome do problema. E o número acompanha o tamanho da estante: com 1.000 livros seriam 1.001 consultas na mesma rota. Repare também no desperdício: são só 4 gêneros no banco, e o código foi buscar o mesmo registro várias vezes.

3. O with('genre'): duas consultas, sempre

O eager loading (carregamento adiantado) inverte a ordem das coisas: em vez de esperar o código pedir o gênero de cada livro, o Eloquent busca todos os gêneros de uma vez, logo depois de buscar os livros, e costura cada gênero no seu livro em memória. Rode a segunda metade do experimento:

Duas consultas — e a segunda é a peça-chave. Os ? são os genre_id distintos que apareceram na primeira consulta: o Eloquent os coleta, busca todos os gêneros correspondentes num único where in e distribui cada objeto para o livro certo. Doze livros ou doze mil, continuam sendo duas consultas.

4. E o JSON passa a vir completo

Com o with('genre') de volta ao service, o mesmo GET /api/books/1 devolve o gênero aninhado, e o cliente resolve tudo em uma requisição só:

Não é coincidência: ao serializar um model para JSON, o Eloquent inclui os relacionamentos que já estão carregados — e só eles. Carregar a relação e expô-la na resposta acabam sendo, aqui, o mesmo gesto. Quer conferir com os próprios olhos? Comente o with('genre') no BookService, repita o curl e veja a chave "genre" desaparecer.

Conceito

Por que essa decisão mora no Service? Porque "de quais dados esta operação precisa" é uma pergunta de negócio, não de HTTP. O controller não deveria nem saber que existe uma tabela genres; o model não sabe em que contexto está sendo usado. O service, que orquestra os dois, é o único lugar com informação suficiente para decidir "nesta listagem, o gênero vem junto".

Boa prática

Eager loading não é "quanto mais, melhor". Repare que o GenreService::listAll() não tem with('books'): a resposta de gênero não expõe os livros, então carregá-los seria trazer 12 registros do banco para jogar fora — o erro oposto, e igualmente caro. A regra prática cabe em uma linha: carregue o que a resposta vai usar, e só isso.

Atenção

O N+1 é traiçoeiro porque só aparece em escala: em desenvolvimento, com 12 livros e o banco na mesma máquina, as 13 consultas se perdem no ruído. Em produção, com milhares de registros e o banco em outro servidor, cada consulta extra é uma ida e volta de rede — e a rota que respondia em 20 ms passa a levar segundos. Para não descobrir isso pelo cliente reclamando, peça ao Laravel que proíba lazy loading fora de produção: um Model::preventLazyLoading(! app()->isProduction()); no método boot() do AppServiceProvider faz qualquer acesso a uma relação não carregada estourar exceção na hora, na sua máquina.

No Passo 9 esse assunto volta com outro nome: quando as API Resources assumirem o controle da saída, o whenLoaded('genre') vai incluir o gênero no JSON apenas se ele tiver sido carregado — garantindo que a camada de apresentação nunca dispare uma consulta escondida por conta própria.

Mão na massa: controllers magros com injeção de dependência

Agora os controllers delegam tudo. Repare no construtor: declaramos que o controller precisa de um service, e o Service Container do Laravel cria e entrega a instância automaticamente — isso é injeção de dependência. A sintaxe private GenreService $genreService direto no construtor (promoção de propriedades, do PHP 8) declara e atribui a propriedade de uma vez só.

Isto é uma refatoração: reorganizamos o código por dentro sem mudar o comportamento por fora (com um único efeito visível bem-vindo: o eager loading do gênero na listagem de livros). As rotas em routes/api.php não mudam nada.

Passo 9 Form Requests e API Resources

Conceito: nunca confie no que chega de fora

Hora de pagar a dívida do Passo 7. Hoje, um POST /api/books sem título quebra com erro de banco (status 500) — a pior experiência possível para quem consome a API. Toda entrada precisa ser validada: campos obrigatórios presentes, tipos corretos, valores dentro das regras.

A boa prática no Laravel é clara: nunca valide dados diretamente no Controller. Crie classes de validação dedicadas — os Form Requests. Cada uma declara suas regras no método rules(), e o Laravel valida antes de o controller sequer ser chamado. Se algo estiver errado, o cliente recebe automaticamente um 422 Unprocessable Entity com a lista de erros em JSON.

Mão na massa: criando os Form Requests

O Laravel aceita tanto uma única string com regras separadas por | quanto um array de regras. Neste material usaremos a sintaxe em array, como ['required', 'string', 'max:255'], adotada nos exemplos da documentação mais recente: cada regra fica separada, a leitura é mais clara e objetos de regra podem entrar no mesmo array sem mudar o formato.

Os arquivos nascem em app/Http/Requests/ (o Laravel criou a pasta agora, lembra do Passo 3?). Atenção a uma pegadinha clássica: o arquivo gerado vem com authorize() retornando false — e, enquanto for false, toda requisição morre num 403 Forbidden antes mesmo de a validação rodar. Nos quatro arquivos, troque o retorno para true: esse método controla quem pode fazer a requisição, e como nossa API é pública nesta etapa, a resposta é "todo mundo":

As regras se leem quase como frases: required (obrigatório), nullable (pode ser nulo), exists:genres,id (o valor precisa existir na coluna id da tabela genres — adeus livros de gêneros fantasmas), in:... (só aceita os valores da lista), min:1 e max:5 (a nota vai de 1 a 5, como pede o enunciado), e sometimes (valide apenas se o campo foi enviado).

Os requests de update têm a mesma estrutura; só as rules() mudam. Como numa atualização o cliente pode mandar apenas os campos que quer alterar, combinamos sometimes e required — "se o campo veio, não pode vir vazio". Para onde ir agora

Algumas ideias para continuar praticando com o BookShelf, em ordem de dificuldade:

  • Filtros: aceitar GET /api/books?status=reading — um where() condicional no BookService;
  • Paginação: trocar get() por paginate(10) no service e observar os metadados que a Resource adiciona ao JSON;
  • Factories e testes: gerar dados falsos com php artisan make:factory e escrever os primeiros testes automatizados com Pest — o trait HasFactory dos models (Passo 6) já está lá esperando por isso.

Próximo módulo

Sua API funciona — mas está aberta ao mundo: qualquer pessoa pode apagar sua estante inteira com um curl. O próximo módulo do curso resolve exatamente isso: middlewares (as camadas que interceptam requisições, do ciclo de vida do Passo 3) e autenticação por tokens com o Laravel Sanctum, transformando o BookShelf em uma API protegida, com usuários, rotas privadas e tokens que expiram. Ele continua exatamente de onde este parou: BookShelf API protegida — autenticação com Laravel Sanctum. Até lá!
